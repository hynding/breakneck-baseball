# Rig, Model & Animation Pipeline — Full Narrative

Verbatim source: the pre-slim CLAUDE.md (also preserved whole in `docs/agent/ARCHITECTURE-FULL.md`).

Player rigs default to a skinned glTF model (`src/game/models/player.glb`), generated by
`tools/build_player.py` → `assets-src/player.blend` → `tools/export_glb.py` and embedded via
`embedded_asset!`; `tests/model_contract.rs` pins it against `model_assets::CLIP_TABLE`
(clip/material/bone names plus tri/bone/size budgets) so the Blender file and the Rust enum can
only drift in ways CI catches.

Regenerating the player model is always this pair, in order — never hand-export from the Blender
GUI, since `export_glb.py` pins the settings (Y-up, NLA-tracks-as-animations, skins) the runtime
loader and `tests/model_contract.rs` depend on:

```sh
blender --background --python tools/build_player.py                       # (re)build assets-src/player.blend from scratch
blender --background assets-src/player.blend --python tools/export_glb.py # export -> src/game/models/player.glb
```

`src/game/present/animation/` keeps the same `AnimClip`/`Playing`/`MoveIntent` API systems write
to, but for glTF rigs it drives Bevy's `AnimationPlayer`/`AnimationGraph` with 150 ms cross-fades
between clips (`PlayerModelId::Blocky` retains the original procedural rig and sampler as the
fallback arm, still reachable via `src/game/present/player/`'s mesh match for a future
humanoid-less theme). `--features dev` swaps the embedded asset for a file-watched path so the
`.glb` hot-reloads on Blender export without a rebuild.

Adding an animation starts with a new Blender action, an `AnimClip` variant, and a `CLIP_TABLE`
row — the compiler then walks you through the rest, since `duration()`/`limb_pose()` are
exhaustive matches with no wildcard arm (plus `looping()` if the clip loops).

One file is pinned outside the layer scheme: `model_assets.rs` and `src/game/models/` stay at
`src/game/` top level, never move them into `present/`, because `embedded_asset!` derives both
the `include_bytes!` path and the registered `embedded://` asset path from the file's own
location (`file!()`) — relocating it breaks the build or, worse, silently breaks model loading
at runtime.

All rig motion flows through `src/game/present/animation/`: systems insert a named `Playing`
clip (`AnimClip`) or write a `MoveIntent` — never rotate rig parts or step transforms directly.
Clips pose limbs *and* can sink the rig root via the `root_drop` channel (`RigBaseY` holds each
rig's resting height; crouches and scoops really lower the body) or lean it via the `root_pitch`
channel composed over the travel yaw (`Dive` for edge-of-reach catches, `Slide` for runners
arriving at a bag). The clip sampler is the seam that let the `AnimationGraph` backend land
behind the same `Playing` API, and `MoveIntent` is the seam for future player-controlled fielding
(CPU choreography writes the same component a controller would).

Players are multi-part rigs recoloured to the fielding/batting team on scoreboard changes;
umpire rigs (`FieldSpec::umpire_positions`, `RigUnit::Umpire`) wear fixed blacks and are skipped
by recolouring, with the `PlateUmpire` crouching through the duel alongside the catcher.

Jersey lettering is procedural (`src/game/present/jersey.rs`): a built-in 5×7 bitmap font draws
each player's surname + number into in-memory RGBA textures (name/number on the back, number on
chest and shoulders) on quads hung off rig roots — `dress_jerseys` re-letters on half-inning
flips, batting-order advances, and substitutions, caching materials per player. Roster names
must therefore be A–Z only.

Presentation is data-driven: `src/game/core/theme.rs` defines `Theme` (UI palette, per-team
`PlayerTemplate`s, ball styling, sky/`ClearColor`, and the `PlayerModelId` that picks the rig
construction) with built-ins behind `ThemeId`, cycled on the menu with T.
